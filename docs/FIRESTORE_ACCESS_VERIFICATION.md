# Firestore 직접 접근 검증

검사 대상은 기존 테스트 주문 2번의 `orderStatuses/2`,
`fulfillmentStatuses/2`, `pickupStatuses/2`입니다.
고객 앱의 디버그 마이페이지 아래에 있는 **Firestore 접근 검사** 버튼을 사용합니다.

## 방법

1. 고객 앱을 Hot Restart(`R`)합니다. 서버 재시작은 필요 없습니다.
2. `shupicktest01@example.com`으로 로그인해서 버튼을 누릅니다.
   세 문서 모두 **본인 문서 읽기 허용**이어야 합니다.
3. 로그아웃 후 다른 UID의 네이버 계정으로 로그인해서 같은 버튼을 누릅니다.
   세 문서 모두 **읽기 차단 (permission-denied)**이어야 합니다.
4. 로그아웃 상태의 마이페이지에서도 같은 버튼을 누릅니다.
   세 문서 모두 **읽기 차단 (permission-denied)**이어야 합니다.
5. 실제 화면 결과를 기록합니다. 연결 실패·문서 없음·캐시 결과는 통과로 계산하지 않습니다.

로그인 정보나 문서 내용은 화면에 출력하지 않습니다. UID는 소유자 비교에만 사용하며,
계정 전환 중 발생한 결과는 폐기합니다. 로그인·로그아웃 후 기존 검사 결과도 초기화됩니다.
버튼을 누르기 전에는 Firebase 요청을 보내지 않습니다. 릴리스 빌드에는 버튼이 없습니다.

## 검증 범위와 현재 상태

- 앱은 현재 Firebase Auth 세션으로 Firestore 클라이언트 SDK의 서버 전용 읽기를 사용합니다.
  관리자 SDK나 FastAPI의 성공 응답을 보안 규칙 검증으로 대신하지 않습니다.
- 데이터·보안 규칙·계정은 변경하지 않습니다. 기존 문서를 읽는 요청만 보냅니다.
- 단위/위젯 테스트는 검사 도구의 판정 로직을 검증할 뿐, 배포된 규칙 통과를 의미하지 않습니다.
- 실제 계정별 직접 읽기 결과는 **확인 대기**입니다.
- 문서 직접 읽기만 검사합니다. 쓰기 차단, 목록 쿼리, 다른 컬렉션 및 서버 API 권한은 별도 검증 대상입니다.
- 콘솔에 게시한 규칙은 주문·배송·픽업 상태의 소유자 읽기만 허용하고 나머지는 거부합니다.
  기존 로컬 `firestore-status.rules`의 재고 읽기 허용 항목과 다르므로 이 파일을 그대로 재배포하지 않습니다.
